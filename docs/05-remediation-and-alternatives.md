# 05 · 修复：卸载与替代方案

**简体中文** · [English](05-remediation-and-alternatives.en.md)

> 本篇是操作指引，写给已确认遇到本文档所述问题的读者。每一步都标注了依据的实测条目；替代方案部分**未在本机实证**，已单独标注。看不懂命令行的，可以把本仓库链接交给你的 AI 助手，让它按本文档逐步讲解或代为执行——每一步都有预期输出可供核对。

## 0. 准备：打开"管理员 PowerShell"

后面第 3、4 节的命令需要在**管理员 PowerShell** 里执行。打开方法（只需做一次）:

1. 按键盘上的 Windows 键，直接输入 `powershell`；
2. 在搜索结果里**右键**"Windows PowerShell"，选"**以管理员身份运行**";
3. 弹出"用户账户控制"询问时点"**是**"。

打开后的窗口标题栏会写着"**管理员： Windows PowerShell**"——有"管理员"三个字才对；没有就关掉重开。

> 怎么执行命令：把本文档里的命令**复制**，在蓝色/黑色窗口里**点右键**即粘贴，按回车执行。每条命令执行后窗口会打印结果，那就是后文说的"输出"。

## 1. 先确认，再动手

本篇的修复只针对本仓库确认的两种情况（`RTLF` 泄漏、`NVRM` 匀速增长）。还没确认过的，先回 [README 的症状对照节](../README.zh-CN.md)——一条命令就能分辨。**确认之前，不要卸载或禁用任何东西。**

---

## 2. 第一步：卸载 OMEN Gaming Hub

操作路径：设置 → 应用 → 安装的应用 → 搜索 **OMEN Gaming Hub** → 点右边的"…" → 卸载。

- **依据**：案例 B 的泄漏源是 OGH 后台进程对 GPU 的高频轮询（实测：它是全机唯一的 `nvml.dll` 消费者，停掉后泄漏停止，详见 03）。卸载是最彻底的"停掉"。
- 这一步假设你不需要 OGH 的其他功能；需要保留的，先看第 5 节的替代方案再决定。

> **顺带说明：OMEN Light Studio**（灯光控制，OGH 的同族组件）。它**与本文档的内核池泄漏无关**——两个泄漏源（`RTLF`/`NVRM`）都不是它。作者卸载它的原因是**用户态 CPU 常驻消耗**：其两个后台进程（`LightStudioHelper`、`LightStudio-background`，合计 64 线程）开机常驻，累计 CPU 时间分别达 2,934 秒与 2,345 秒——而灯光只在设置时需要它，设置完并不需要它持续运行。如果你的灯光方案已经调好、不需要再动，可以连同卸载（同一操作路径搜 "OMEN Light Studio"）；灯效已经写入硬件/驱动的，卸载控制端不影响已保存的灯效。

---

## 3. 第二步：清除残留的 rtf64 驱动（卸载 OGH 不会带走它）

**实测结论（Finding #8）**：`rtf64` 是独立注册的系统服务，OGH 的卸载器不管它——**只做第一步的话，RTLF 的 530 MB 还在**。

在"管理员 PowerShell"（见第 0 节）里执行：

```powershell
sc.exe config rtf64 start= disabled
```

预期输出：`[SC] ChangeServiceConfig 成功`。

然后**重启电脑**。重启后这个驱动不会再加载（实测：`RTLF` 归零，见 02 第 6 节）。

两个常见疑问：

- **"我在网卡属性里取消了 Realtek LightWeight Filter 的勾选，不行吗？"**——不行。取消勾选只断开绑定，服务本身照样开机加载；机制见 02 第 5 节。
- **想连驱动文件一起删掉（可选，更彻底）**:
  ```powershell
  sc.exe delete rtf64
  pnputil /delete-driver oem43.inf /uninstall
  ```
  注意 `oem43.inf` 是本机的编号，你的机器可能不同：先执行 `pnputil /enum-drivers`，在输出里找 Provider 为 Realtek 的那条，用它的"发布名称"替换 `oem43.inf`。

---

## 4. 第三步：验证修好了

重启后，在"管理员 PowerShell"里用本仓库的脚本复测（只读，不改任何东西）:

```bash
python scripts/pooltag.py after.json
```

对照下表：

| 看什么 | 预期 |
|---|---|
| `RTLF` | **消失或为 0**（实测对照：处置前 530 MB，处置后 0) |
| `NVRM` | 还在列表里，但**不再增长**（处置后稳定在约 59 MB；隔一小时再跑一次，两次数值应基本持平） |
| 网络 | 正常（`rtf64` 是旁路层，禁用它不会断网——见 02 第 5 节的推论 1) |

## 5. 替代方案

⚠️ **本节未在本机实证**，是按功能位给出的通用替代；标了"需自查"的项目，请先确认对你的机型有效再依赖。

OGH 卸载后，它的部分功能可以用下面这些开源项目补上。**注意两点：它们只能部分实现 OGH 的功能，且可能不支持所有机型**（用前先到各项目的 issue 区确认自己的型号）。

| 项目 | 能补上的功能 |
|---|---|
| [OmenMon](https://github.com/OmenMon/OmenMon)（专为 OMEN 机型） | 性能模式 / 风扇 / 背光 |
| [FanControl](https://github.com/Rem0o/FanControl.Releases) | 风扇曲线 |
| [LibreHardwareMonitor](https://github.com/LibreHardwareMonitor/LibreHardwareMonitor) | 硬件监控（**先看下方警告**） |
| [OpenRGB](https://openrgb.org) | RGB 灯光 |
| Steam Link / Moonlight | 远程游戏串流 |

> **边界声明（作者注，未逐一实测各项目对每个机型的支持）**：上表及目前社区已知的其他 OMEN 开源工具，普遍只支持**第 7 代及以后**的 OMEN 机型；**第 6 代及更早机型目前没有成熟的开源替代方案**——这些机器上，对应功能要么继续用官方工具，要么放弃该功能。第 6 代及更早的读者，清理 OGH 前先确认愿意放弃对应功能。

> ⚠️ **装替代监控面板之前必读（本仓库的核心教训）**：案例 B 的机制是"监控进程高频轮询 GPU → 驱动的分配跟不上释放"。**任何**以固定频率查询 GPU 的软件（灯效、帧率悬浮窗、游戏助手）都可能成为下一个同样的泄漏源。优先选轮询频率可调的工具、把间隔调长，或者干脆少装监控面板。
