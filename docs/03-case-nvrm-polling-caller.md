# 03 · 🅱️ 案例 B：调用方触发的泄漏（NVRM，1.77 GB）

[English version](03-case-nvrm-polling-caller.en.md)

> 📌 **要点**：匀速泄漏的驱动往往是无辜的执行者。先花 10 秒查"谁在调用它"，可能省掉一次无意义的驱动重装。

---

## 1. 现象

`NVRM` 标签缓慢增长：**空闲时 6–8 MB/h，使用中最高 29 MB/h**，71 小时累积到 **1.77 GB**。分配 2.72 亿次 / 释放 2.67 亿次（释放率 98%——匀速累积型泄漏的典型形态：绝大多数都还了，**净增速率才是问题**）。

> 与案例 A 对照：A 是"分配了不还"（释放率 9.7%），B 是"还了但分配更快"（释放率 98% 但净增长期持续）。两种形态对应两种排查思路：前者查"谁持有"，后者查"谁在驱动流量"。

## 2. 归属

`NVRM` 命中两个驱动：`nvlddmkm.sys`（主）与 `nvpcf.sys`——NVIDIA 显卡内核驱动（匹配计数 2，边界判定后无假阳性）。

## 3. 关键一步：查调用方，而不是查驱动

显卡驱动自己不会平白增加负载。NVIDIA 在用户态暴露了查询接口 `nvml.dll`（NVML，nvidia-smi 同源的监控库）。**谁加载了它，谁就在以某种频率查询 GPU**：

```powershell
tasklist /m nvml.dll
```

实测输出（处置当日）：

```
映像名称                     PID    模块
=========================================
OmenCommandCenterBackgrou    44468  nvml.dll
```

**全机只有一个进程**：OMEN Gaming Hub 的后台进程（工作集 331 MB，开机常驻）。硬件监控面板类软件按固定频率轮询 GPU 利用率/温度/频率——每次查询都经 NVML 进入驱动、产生内核池分配。

## 4. 处置与验证（A/B 对照）

处置：结束该进程（其后台服务此后随 OGH 一起被卸载——用户本就不需要 OGH 的功能）。

三阶段速率探针（`scripts/rate_probe.py`，CSV 落盘）：

| 阶段 | NVRM 占用 | 说明 |
|---|---|---|
| 基线（探针自检） | 59.09 MB | 处置后 |
| 12.3 分钟窗口 | 59.99 MB | 杀进程后 |
| 再观察 | 59.25 MB | 稳定在 ~59 MB |

处置后 `NVRM` 稳定在 **~59 MB 不再增长**；重启后从干净基线起步，无复发（对照处置前 71 小时累积 1.77 GB 的斜率）。

### ⚠️ 历史观察（未落盘）

处置会话中曾观察到**连续 10 次读数逐字节相同**（59.25 MB 不变，间隔约 1 分钟）——判据二所述的"平坦读数"最强证据形态。该逐次记录未落盘（落盘 CSV 只有上述三阶段汇总点），本仓库按**历史观察**等级引用；"停止增长"的判定以落盘的三阶段数据为准。

## 5. 结论与边界

| 陈述 | 等级 |
|---|---|
| OGH 后台进程是全机唯一 nvml.dll 消费者 | **实测** |
| 停止该进程后 NVRM 停止增长 | **实测**（三阶段数据） |
| 泄漏由轮询触发（调用频率 → 分配速率） | **推断**（机制层面未做栈采样验证；"想定论需 WPR 栈采样"，见 01 附注） |
| NVIDIA 驱动在此场景下"有责任"吗 | 驱动按请求服务；**处置调用方即可**，无需动驱动 |

## 6. 与社区报告的差异

网上已有的 NVRM 泄漏报告（WSL nvidia-smi 触发、某版本 Game Ready 驱动泄漏）都归因于**驱动自身或特定触发工具**，处置是"换驱动版本"。本案例的增量在于：**普通桌面环境下，第三方监控面板的轮询就足以造成累积泄漏**，且用一行 `tasklist /m` 即可定位调用方——先查调用方再考虑动驱动。
